## 1. 背景

- Sansanコンタクトの蓄積が進み、CSV単位の都度処理から、検索・照会・分析に耐えるデータベースへの移行が必要になった

- 理想は「営業がナレフルチャットに投げるだけで完結する」動線。ただしナレフルチャットでどこまで実現できるか（蓄積・照会・自動同期）は未検証
- 親文書「20260703_PLAN_情報統合基盤_RAGと構造化の全体設計_v3.md」は欠落中（KNOWLEDGE_MAP「欠落・要回収」）。回収して本書と突合する

## 3. 設計の骨格（たたき台）

```
Sansan（一次データ）──CSVエクスポート──> 正本DB（置き場は Q1）
                                        ├─ 配布コピー ──> ナレフルチャット参照ファイル（照会用）
                                        └─ 紐付け ────> BU/SI一覧・パイプライン（連携範囲は Q4）

営業 ──CSV/メモ──> ナレフルチャット（整理エージェント）──タブ区切り出力──> 正本DBへ追記
```

ナレフルチャットは「入口（構造化）」と「出口（照会）」のUI。データベース本体はナレフルの外に置く。理由: ナレフルは参照ファイルの手動差し替えでしか知識を更新できないため、正本を持たせると想起（R2）が月次手動運用に縛られる。
対社内の説明では「ナレフルに聞けば分かる」を前面に出し、リポジトリ正本の存在は運用側の実装詳細として扱う（P7）。

## 4. 最終ゴール（1文）

> **営業がナレフルチャットにコンタクト情報を投げるだけで整理・蓄積が完結し、「○○社の誰に会った？」に出典付きで答えられるコンタクトデータベースが、正本1か所で常に最新に保たれる。**

## 6. スコープ

**含む**
- コンタクトDBのスキーマ設計（SPEC起草）
- 既存SansanエクスポートCSVの取り込み・名寄せ
- ナレフルチャットのハック可能範囲の検証（G5）
- 週次運用フロー（整理→追記→配布コピー差し替え）の設計
- 照会用配布コピーの生成スクリプト

**含まない**
- Sansan API連携の実装（P5の制約。Q7として将来検討）
- SFA/CRM導入の検討
- パイプライン・SENDOへの書き戻し
- メール配信等の営業施策そのもの
- BU/SI一覧・パイプラインとのコンタクト紐付け（2026-08-13回答で初期構築から除外。時期はQ4として残す）

## 7. 制約

| # | 制約 | 影響 |
|---|---|---|
| C1 | ナレフル参照ファイルは手動差し替え。自動同期APIは現時点で確認されていない | 同期頻度は週次〜月次が現実線 |
| C2 | ナレフルの知識蓄積は「処理済みコンタクト集を月次で参照ファイルに追加」する手動運用。チャット横断の自動記憶はない前提で設計する | モックv2既知の仕様 |
| C3 | 長いCSVは後半の処理が雑になる（モックv2既知の限界） | 取り込みは10〜20件単位に分割 |
| C4 | Sansanエクスポートの列構成はSansan側の仕様変更で変わりうる | 取り込み処理は列名マッピングを設定化し、ハードコードしない |
| C5 | 個人情報を含む（P6） | 公開リポジトリ・外部サービスへのアップロード禁止。配布コピーの項目は線引きする（Q5） |
| C6 | ランク定義（A〜E）はガイドライン準拠だが見直されうる | スキーマ・スクリプトにハードコードしない |
