- ナレフルチャットのRAGで辻褄を合わせる設計をやめ、**GitHubリポジトリ＋Claude Codeで完結する構成に転換する**

## 3. 設計の骨格（たたき台）

```
Sansan ──Open API（Actions定期実行・キーはSecrets）──> 専用リポジトリ（正本DB）
                                                          ↑ 構造化コミット
営業メール ──Gmailフィルタ──> 所定ラベル ──Gmail MCP──> Claude Code（整理・名寄せ）

照会「○○社の誰に会った？」──> 高山さん ──> Claude Codeセッション ──> 出典付き回答

（ナレフルチャット＝上記の再現用モック。正本から配布コピーを渡して動かす。正本更新には関与しない）
```

正本・処理・照会をすべてGit＋Claude Codeに寄せることで、初版で問題だったナレフル側の制約（手動差し替え・月次フラット蓄積・長CSV劣化）が構造ごと消える。名寄せ・履歴・出典はGitの得意分野で解く。

---

## 4. 最終ゴール（1文）

> **営業接点（Sansanコンタクト・営業メール）が人手を介さず専用リポジトリに集まり、Claude Codeが整理・名寄せ・照会を担う。「○○社の誰に会った？」に出典付きで答えられる正本が、1か所で常に最新に保たれる。**

## 5. 受け入れ基準

| # | 条件 | 検証方法 |
|---|---|---|
| G1 | 既存Sansanコンタクトの全件が正本DBに取り込まれ、重複（同一人物・同一社）が名寄せされている | 件数突合＋重複検出スクリプト |
| G2 | スキーマが文書化されている（安定ID・ランク・KWタグ・進捗メモ・出典） | SPEC文書の存在と実データとの一致 |
| G3 | 「○○社の誰に会った？」にClaude Codeセッションが出典付きで答えられる（高山さん経由運用で1サイクル） | 実照会の通し確認 |
| G4 | Sansan定期取得（Actions）が人手ゼロで回っている（API不可の場合: CSV手順が週次で回っている） | 2サイクル連続の自動実行ログ |
| G5 | 営業メールがフィルタ→取り込み→正本反映まで通っている | 1サイクル実運用 |
| G6 | 個人情報の線引き（照会出力・モック配布コピーに載せる項目）が定義され、守られている | 出力の項目監査 |
| G7 | ナレフルモックが正本から生成した配布コピーで再現できる（更新手順が文書化されている）※優先度低 | モックでの照会テスト |

## 6. スコープ

**含む**
- 専用リポジトリの設計（構成・アクセス権・CLAUDE.md）
- コンタクトDBのスキーマ設計（SPEC起草）
- Sansan取得ワークフロー（Actions定期実行。API不可時はCSV代替手順）
- 営業メール取り込みフロー（フィルタ設計＋Gmail MCP読み取り）
- 既存コンタクトの取り込み・名寄せ
- 照会運用（高山さん経由）の手順化

**含まない**
- 営業が直接照会するUI（Q7・後段）
- BU/SI一覧・パイプラインとの紐付け（Q4・後回し継続)
- SFA/CRM導入の検討
- ナレフルモックの高度化（再現に必要な範囲のみ維持）

## 7. 制約

| # | 制約 | 影響 |
|---|---|---|
| C1 | Sansan Open APIは契約プラン依存。**可否未確認** | 最優先で確認（Q1）。不可ならCSVエクスポート経路で開始し、取得層のみ後日差し替え |
| C2 | CCWの環境変数は環境利用者全員が読める | APIキーはGitHub Actions Secretsのみ。CCWセッションからAPIを直接叩かない |
| C3 | 専用リポジトリはプライベート必須（P6） | 配布コピー（モック用含む）を作る場合はQ5の線引きを先に確定 |
| C4 | メールフィルタの設定はGmail側の管理権限に依存 | フィルタ仕様（Q6）を情シス/管理者と握る |
| C5 | ランク定義（A〜E）はガイドライン準拠だが見直されうる | スキーマ・スクリプトにハードコードしない |
