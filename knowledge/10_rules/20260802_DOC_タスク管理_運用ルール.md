# タスク管理 運用ルール（GitHub Issues + Project 一元化）

**作成日**: 2026-08-02
**正本**: 本ファイル（snj-knowledge / knowledge/10_rules/）
**経緯**: 週次Excelスナップショット方式（25-11-14〜26-07-27、23シート）を廃止し、GitHub Issues + 単一GitHub Projectに移行。2026-08-02に未完了37件を移管済み（§5）。

## 1. 原則

- 業務タスク全般を**1つのGitHub Projectで一元管理**する。Excel・個人メモでのタスク台帳は作らない
- タスクの実体はIssue。Projectはビュー（俯瞰・並べ替え・週次レビュー）に使う
- 完了はIssueのclose。履歴・経緯はIssue上に残る（Excelのような週次スナップショット保存は不要になる）

## 2. 置き場ルール

| タスクの種類 | 起票先 |
|---|---|
| EEZO関連（EC運営・SI・Shopify・分析） | `rtakayama1293/eezo-ops` の Issues |
| それ以外の業務タスク全般（SENDO・DENBA・BLING・契約・稟議・調査・社内制度など） | `rtakayama1293/snj-knowledge` の Issues |

- 迷ったら snj-knowledge に置く（後から Transfer issue で移せる）
- 両repoのIssueを同一Projectに紐づける

## 3. ラベル体系（両repo共通）

Excel時代の3軸をラベルで引き継ぐ。

| ラベル | 意味 |
|---|---|
| `インパクト:高` | 主要SI or 業務全体に直結 |
| `インパクト:中` | 主要SI |
| `インパクト:低` | それ以外 |
| `緊急度:高` | 今週 |
| `緊急度:中` | 2週間以内 |
| `緊急度:低` | それより先 |
| `仕組み` | 仕組み化（再現可能なフロー・自動化を作る）タスク |

- eezo-ops は既存の体系（`L0-blocker`〜`L2-supply`・`at:*`・`判断待ち`・`期日あり`・`SI`）を**併用**する。L*は着手優先度、インパクト/緊急度は全社ビューでの比較用
- 所要時間見積（h）とタスク追加日はIssue本文に書く（移管分は旧Excel idも記載）

## 4. 運用フロー

1. **起票**: タスク発生時にIssue作成 → インパクト/緊急度ラベル付与 → Projectに載る（auto-add）
2. **週次レビュー**（旧Excelの週次更新の代替）: Projectビューで全体を俯瞰し、緊急度ラベルの見直し・完了close・不要issueのclose（not planned）を行う
3. **集計**: 工数合計・インパクト×緊急度マトリクス等が要る場合はCCWセッションでIssue一覧から生成する（Excelの集計表の代替）

## 7. Projectへの自動追加の仕組み（手動セットアップ・要実施）

Freeプランでは**Projectのauto-add workflowは1本のみ**のため、2repo構成では次のように分担する。

| repo | Projectへの追加方法 |
|---|---|
| eezo-ops | Project組み込みのauto-add workflow（既存設定を継続） |
| snj-knowledge | GitHub Actions `.github/workflows/add-to-project.yml`（issue開設時に `gh project item-add` で追加） |

初回セットアップ（Web UIで手動）:

- [ ] `.github/workflows/add-to-project.yml` の `PROJECT_NUMBER` をProject番号に書き換える
- [ ] classic PAT（scope: `repo` + `project`）を作成し、snj-knowledge の Actions secret `ADD_TO_PROJECT_PAT` に登録する
- [ ] 移管済みIssueをProjectに追加（自動追加は既存Issueに遡及しないため、初回のみ手動で「Add items from repository」）
- [ ] 必要ならProjectカスタムフィールド（所要時間・追加日）を作り、ラベル/本文から転記

なおCCW/Claude CodeのGitHub MCPにはProjects v2の操作ツールが無いため、Project本体の設定変更は常にWeb UIで行う。
