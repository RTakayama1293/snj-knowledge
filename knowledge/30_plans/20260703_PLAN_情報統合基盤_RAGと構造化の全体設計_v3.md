## 1. 変わらない原則（v1〜v2から継承）

- **一入力二出口**: 生データを1回だけL1に溜め、出口はRAG回答と台帳行の2つ
- **フロー/ストック分離**: 経緯（①案件進捗・②仕入開拓）はフロー、③条件・合意はストック。ストックの正本はマスタ
- **RAGは構造化を代替しない**: カネと掟は100%ゾーン。AIは案まで、確定は高山（週次・月曜）
- **RAGの3役割**: R1構造化の補助輪（最優先）／R2想起Q&A（ダッシュボードが大部分を代替）／R3生データアーカイブ
- **営業の入口は3つだけ**: Sansanコンタクト／sales@転送／共有フォルダ
- **ShopifyとSENDOの線引き**: Shopify=取引実行層（反映先）、SENDO=管理台帳層（正本）

## 2. v3の中心: L2処理層の実装方式が定まった

v2までのL2は「定型プロンプト＋ナレッジパック＋差分データの3点渡し」という抽象設計だった。モック構築（案件整理アシスタント）により、これが**ナレフルチャットの標準機能だけで実装できる**ことが具体化した。

### 2.1 v2設計とモック実装の対応表

| v2の設計要素 | ナレフルチャットでの実装 | 状態 |
|-------------|------------------------|------|
| ナレッジパック（用語・マスタ・お作法） | 参照ファイル3本（参照01〜03） | 実装済み |
| 定型プロンプト | ベースプロンプト（構造化/照会の2モード） | 実装済み |
| 差分データの投入 | チャットへのCSV添付・本文貼付（週次） | 実装済み |
| 出力①②③ 台帳行更新案 | タブ区切り出力（Excel直貼り） | 実装済み・検証中 |
| 出力④⑤ マスタ/ルール変更候補 | 見出し必須出力＋実行後分岐で判定 | 実装済み・検証中 |
| 変更検知アラート（v2ではP3想定） | **実行後分岐→オーナー宛メール送信** | 実装済み・検証中 |
| 誤用ガード | 実行前分岐→対象外は案内表示で終了（AI非実行） | 実装済み |
| R2想起（過去分照会） | 月次「処理済みコンタクト集.md」を参照ファイルに追加 | 未実装（運用で段階導入） |

### 2.2 モックが前倒しした論点

- **検知アラートはP3の自動化を待たなくてよい**。実行後分岐のメール通知が動けば、週次バッチの目玉機能（出力④⑤の通知）はP1.5相当で稼働する。Webhook→Slack化（田嶋・門永さんへの直接通知）は次段
- **2段パイプライン（抽出→SIマッチング・集計）の分割余地**が標準機能（次エージェント連続実行）で確保されている。1エージェント詰め込みで精度が落ちた場合の逃げ道が最初からある
- **R2の実装形が具体化**: 「処理済みコンタクト集を月次で参照ファイルに追加」という低コスト運用。sales@自動集約（P2）を待たずに照会モードの価値検証ができる

### 2.3 モックの合否基準（ガイドから転記・v3の検証ゲート）

分類精度／列ズレ／推測混入／KW規律（辞書外は【新規KW候補】経由）／検知感度。この5観点の検証結果がP1完了判定になる。

## 3. 正本と配布コピーの管理原則（v3新設）

ナレッジパック（参照01〜03）の先行実装により、同じ知識が「プロジェクト知識」「ナレフル参照ファイル」「SENDO内シート」に併存し始めた。二重管理で腐るのを防ぐため、以下を原則とする（方針案）。

| 知識 | 正本の置き場 | 配布コピー | 更新トリガー |
|------|------------|-----------|-------------|
| 用語集 | プロジェクト知識（用語集.md） | 参照01 | 新用語の発生時 |
| お作法・ルール集 | プロジェクト知識（ルール集.md・新設） | 参照01の「お作法」節 | 出力⑤ルール変更候補の人間確定時 |
| KWタグ辞書 | SENDO（SIマスタと同居） | 参照02 | 【新規KW候補】の採用時 |
| SI一覧 | SENDO SIマスタ（**ボトムアップBU一覧を正とする**） | 参照02 | BUの確定・改訂・引退時（4章ライフサイクル） |
| ステージ定義・出力フォーマット | 計数管理基盤_全体設計書 | 参照03 | 設計書改訂時 |
| 価格順位表・仕入先評価 | SENDOマスタ（門永Excel由来） | （参照ファイル化しない※） | 出力④の人間確定時 |

※価格・条件のマスタは100%ゾーンのため、鮮度管理できない配布コピーを作らない。エージェントに価格判断をさせず、「変化の検知」だけをさせる現行設計を維持する。

**運用ルール（方針案)**: 正本を更新したら、次回の参照ファイル差し替えをNotionタスクに起票する。参照ファイル側を直接編集しない（編集した場合は同日中に正本へ逆反映）。

## 4. SIライフサイクル — ボトムアップ運用（v3新設）

SI一覧は「整った完成品」ではなく、**実案件から立ち上がり、検証され、更新され続けるボトムアップの生き物**として運用する。トップダウンPF（v5.1）方式からの転換。週次抽出ループの出力がSI一覧そのものを育てる構造にする。

### 4.1 ライフサイクル定義

```
[タネ]        実案件・実接点（受注/商談/サンプル転換）が発生
   ↓ 単価・頻度・KWを構造化（si-target-definitionスキル：粒度判定＋簡易定義）
[BU仮説]      BU-xx として暫定採番・一覧に登録。不明項目リスト付き
   ↓ 検証＝不明項目の実測（リピート頻度・成立要因の分解・TAM確認）
[確定SI]      単価・頻度が収斂したら正式採番。6面フル定義＋試算テンプレート接続
   ↓ 案件が途絶える／前提が崩れる
[待避]        一覧から外すが廃止しない。案件が再発生したらBU化して復帰
```

### 4.2 週次抽出ループとの接続（SIを育てる3つの入力経路)

| 経路 | 発生源 | 動作 |
|------|--------|------|
| **a. マッチなし検知** | 出力①のSIマッチングで「どのBUにも40%未満」の案件KWパターンが継続 | 新BU候補として報告（クラスタSI発見。モックに実装済みの注記どおり） |
| **b. 実測更新** | 台帳の実績（リピート発注・受注確定）がBUの推定値（頻度・単価）と乖離 | BU定義の改訂候補として報告 |
| **c. 横展開の種** | L3-a型BU（BU-03/05/06）の起点顧客で新しい成立要因が判明 | 横展開セグメント（L2）の公開条件に追記 |

いずれも**AIは候補まで、確定は高山**（マスタ変更候補・ルール変更候補と同じガバナンス）。確定したらSENDO SIマスタ（正本）→参照02（配布コピー）の順で更新する（3章の原則）。

### 4.3 更新サイクル

- **週次（月曜）**: a/bの候補を確認。BU一覧の推定値→実測値の置き換え
- **四半期（蜂巣さん定例）**: BU仮説→確定SIの昇格判定、待避判定、正式採番。si-channel-briefing形式で報告
- **旧PFのSI**: 実案件の裏付けがないものは待避扱い（BU再構成v1の3章）。復帰条件は「紐づく案件の発生」のみ

### 4.4 これが解くもの

- 「SIが整っていないから案件管理が始められない」の逆転——**案件からSIが生まれる**ので、整備を待たずに運用開始できる
- SI一覧の陳腐化防止——参照02が古いままエージェントが誤マッチする事故を、更新トリガーの明文化で防ぐ
- クラスタSI構想（5/14引き継ぎの2類型）の実装——「案件20〜30件到達後に分析」を待たず、週次のマッチなし検知で常時回る

## 6. アーキテクチャ（v3版・実装方式を明記)

```
【L0 発生源】商談 / メール / Slack（社内サンプル運用）/ 海外チャットスクショ / 電話

【L1 溜める】Sansanコンタクト ＋ sales@ ＋ 共有フォルダ ＋ Slackエクスポート
     │
【L2 処理】= ナレフルチャット「案件整理アシスタント」（モック検証中）
     │   構成: ベースプロンプト ＋ 参照01〜03（ナレッジパック配布コピー）＋ 週次差分データ添付
     │   ガード: 実行前分岐（対象外は案内表示・AI非実行）
     │
     ├─ 出力① 案件台帳の行更新案（タブ区切り→SENDO）
     ├─ 出力② 仕入先開拓台帳の行更新案（同上）
     ├─ 出力③ サンプル台帳の行更新案（同上・13列版）
     ├─ 出力④ 【マスタ変更候補】 ⚠要人間確認 ─┐
     └─ 出力⑤ 【ルール変更候補】 ⚠要人間確認 ─┴→ 実行後分岐→高山宛メール自動通知
     │
     高山が週次（月曜）確認・確定 ※カネと掟は100%ゾーン
     │        確定したルール改訂 → 正本（ルール集.md）→ 参照01差し替え（3章ループ）
     │        マッチなし・実測乖離 → BU候補/改訂 → SIマスタ → 参照02差し替え（4章ループ）
     │
【L3 正本】
  SENDO … 案件/仕入開拓/サンプル台帳・マスタ・収支・ダッシュボード
  Shopify … 出荷イベント実行台帳（受注・¥0サンプル下書き注文・顧客レコード・B価格反映）
  ダッシュボード … R2の大部分を代替。RAGへの頻出質問→項目化ループ
```
